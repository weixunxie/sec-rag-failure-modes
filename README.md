# SEC RAG Failure Modes

A research repository for evaluating retrieval-augmented generation (RAG) failure modes when answering financial questions about SEC 10-K filings.

## Research Goal

Compare three retrieval strategies and classify where RAG systems fail — distinguishing **retrieval-stage errors** (wrong entity, wrong year, semantic mismatch) from **generation-stage errors** (hallucination, reasoning errors, incomplete synthesis) — when answering questions about 10-K annual reports.

- **OpenAI API key** — for `text-embedding-3-small` embeddings, `gpt-4o-mini` answer generation, and LLM-as-judge evaluation

## Retrieval Strategies

### 1. Vanilla
Pure cosine similarity over the full `sec_filings` collection with no metadata filters. Baseline that treats all chunks equally regardless of company or year.

### 2. Metadata-Filtered
Pre-filters the collection by `ticker` and/or `year` before running similarity search. Eliminates off-entity noise for single-company questions.

### 3. Task-Aware
Routes to the appropriate sub-strategy based on question type:
- `single_fact` / `risk_factor` → metadata-filtered with company + year
- `cross_year` → split-budget retrieval: top-k/2 from each of the two years
- `cross_company` → split-budget retrieval: top-k/2 from each of the two companies

## Error Taxonomy

### Retrieval-Stage Errors
| Type | Description |
|------|-------------|
| `WRONG_ENTITY` | Retrieved chunks from wrong company |
| `WRONG_YEAR` | Retrieved chunks from wrong fiscal year |
| `WRONG_SECTION` | Retrieved from wrong 10-K section |
| `INSUFFICIENT_COVERAGE` | Retrieved chunks lack the needed evidence |
| `SEMANTIC_MISMATCH` | High cosine similarity but topically irrelevant |

### Generation-Stage Errors
| Type | Description |
|------|-------------|
| `HALLUCINATION` | Model states facts absent from any retrieved chunk |
| `REASONING_ERROR` | Evidence present but model draws wrong conclusion |
| `INCOMPLETE_SYNTHESIS` | Model ignores some relevant retrieved chunks |
| `CITATION_FABRICATION` | Model cites chunk IDs not in the provided context |
| `OVERCONFIDENCE` | High confidence reported despite weak evidence |

## Chunking Design

Section-aware chunking respects the structure of SEC 10-K filings:

- **Item 1** → Business
- **Item 1A** → Risk Factors
- **Item 7** → MD&A
- **Item 7A** → Market Risk
- **Item 8** → Financial Statements
- **Item 9A** → Controls

Each section is chunked at **800 tokens** with **100-token overlap**, splitting at paragraph boundaries where possible.

## Data Sources

All filings are downloaded directly from [SEC EDGAR](https://www.sec.gov/cgi-bin/browse-edgar) using the public REST API (`https://data.sec.gov/submissions/`). No third-party data providers are used.

Per SEC guidelines, requests include a `User-Agent` header and are rate-limited to ~7 requests/second.

## Results

Evaluated on 40 questions × 3 strategies = 120 answer-evaluation pairs. Scores are on a 0–2 scale (LLM-as-judge via `gpt-4o-mini`).

| Strategy | Correctness | Citation Faithfulness | Evidence Coverage | % Correct | % Retrieval Err | % Generation Err |
|----------|------------|----------------------|-------------------|-----------|----------------|-----------------|
| Vanilla | 1.68 | 0.68 | 0.92 | 50% | 10% | 40% |
| Metadata Filtered | 1.52 | 0.57 | 0.90 | 40% | 2.5% | **57.5%** |
| **Task-Aware** | **1.75** | **0.82** | **1.10** | **62.5%** | **0%** | 37.5% |

**Key takeaways:**
- Task-Aware retrieval achieves the highest correctness (62.5% fully correct) by allocating retrieval budget appropriately per question type
- Metadata-Filtered surprisingly underperforms despite the lowest retrieval error rate — over-filtering narrows the context too aggressively, shifting failures to the generation stage
- Vanilla has the most retrieval errors (10%, mostly `WRONG_ENTITY`) but still outperforms Metadata-Filtered overall, suggesting generous context beats narrow-but-precise context for diverse question types
- Generation-stage errors dominate across all strategies (~40–57%), indicating that prompt and model improvements are higher-leverage than retrieval tuning alone
